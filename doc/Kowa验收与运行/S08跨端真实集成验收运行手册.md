## 1. 适用范围与水位分层

- 适用：单 macOS 账号、单机 Server + 单 Runner、本机 PostgreSQL 17.11 与本地 Artifact Store 上执行的跨端真实验收（W1—W9 与权限/隔离负向场景）。
- 与 [S07 本机运行与恢复手册](S07本机运行与恢复手册.md) 的关系：S07 手册仍是**本机运行配置（§3）、健康与水位（§4）、评测后端（§5）、运行编排（§6）、备份恢复（§7）、演练（§8）、实测记录（§9）、水位清单（§10）与风险声明（§11）**的权威；本手册只补 S08 增量的三件事：GitHub App 环境、验收堆栈、S08 交付的 installation 适配器。两处冲突时以本手册为准（仅限 S08 增量）。
- 水位分层（S08 必须分别记录，不得混称）：
  - **真实层**：真实 GitHub App（用户创建/安装/授权）、真实浏览器 OAuth 登录、真实 Runner + 本机 Provider CLI、真实 `git push`/PR/Review/merge。证据 ID 来自用户返回与新发运行。
  - **隔离层**：Docker 一次性 PostgreSQL、本地受控 bare 仓、stub OAuth、scripted provider——S00—S07 的自动与隔离证据；只证明实现与门禁，不证明真实外部事实。

| installation ID | 安装后的 `https://github.com/settings/installations/<id>` URL 中的 `<id>`（十进制） |
| 环境变量（只在本机 shell 导出，**不进 git、不进证据、不进截图**） | `KOWA_GITHUB_APP_ID`（App ID 十进制）、`KOWA_GITHUB_APP_PRIVATE_KEY_PATH`（私钥路径）、`KOWA_GITHUB_CLIENT_ID`、`KOWA_GITHUB_CLIENT_SECRET` |
| 机器 gh 身份（publish_pr 与只读观测） | keyring 活动账号 `SnWalker`（numeric id `135722937`）；`ssh -T git@github.com` 必须回 `Hi SnWalker!` |
| 第二个真人账号（Review） | `snflyer`（numeric id `277460407`，write 协作者，无 admin；Reviewer 不能是 PR 作者） |

注意：

- 私钥与 client secret 属于部署材料；仓库的 `check-secret-leaks.sh` 门禁会把任何凭据形状字面量判为失败，因此**不得**把它们写进任何仓库文件或证据。

## 3. 验收堆栈（`scripts/kowa-acceptance-stack.sh`）

一键启动真实验收所需的四个进程/组件；它不安装或授权 App、不代替用户登录、不合并 PR、不虚构任何外部事实。

```bash
# 用户先在当前 shell 导出 §2 的四个变量，然后：
bash scripts/kowa-acceptance-stack.sh --with-runner          # 首次（含 Runner）
bash scripts/kowa-acceptance-stack.sh --with-runner --fresh-db # 从空数据库重来
```

| 组件 | 取值/位置 |
| :--- | :--- |
| Web origin（可信 HTTPS） | `https://127.0.0.1:8443`（`KOWA_ACCEPTANCE_ORIGIN` 可改；必须与 App 回调一致） |
| 控制面 | `http://127.0.0.1:8080`（真实 `cmd/server`，未替换任何适配器） |
| 运行目录 | `/tmp/kowa-s08-run`（`KOWA_ACCEPTANCE_RUN_DIR` 可改）：`bin/`、`tls/`、`materialize/`、`runner/`、`logs`、`runtime-token`（0600，不打印） |
| 本地证书 | `$RUN_DIR/tls/origin-cert.pem`（首次生成后复用，指纹稳定）；浏览器/钥匙串**信任一次**（仅用户） |
| PostgreSQL | 容器 `kowa-s08-acceptance-pg` + 卷 `kowa-s08-acceptance-pgdata`（跨重启保留；`--fresh-db` 丢弃） |
| Runner | `KOWA_RUNNER_PROVIDER=claude`（本机 `claude` CLI），能力集 = 固定流程的九个 capability；`KOWA_RUNNER_REPOSITORIES` 绑定两个沙箱仓 id |
| 运行时凭据 | 启动脚本生成并持久化在 `$RUN_DIR/runtime-token`；不打印、不进仓库 |
| 仓库登记 | `KOWA_REPOSITORY_REGISTRY=1401511579=git@github.com:SnWalker/kowa-sandbox.git,1413481670=git@github.com:SnWalker/kowa-sandbox-knowledge.git`（**SSH**；见下方运输说明） |

运输说明（2026-10-16 复跑实测，脚本默认值已按此修正）：本机 Git 身份走 SSH（`gh` 协议 ssh + 磁盘密钥），材料化按设计不注入任何凭据且设 `GIT_TERMINAL_PROMPT=0`（`internal/materialize/git.go`），因此 `https://github.com/…` 对 **private** 知识仓无法取得口令（实测 `fatal: unable to get password from user`），且当日直连 `https://github.com` 持续失败而 SSH 稳定。`KOWA_ACCEPTANCE_PROJECT_CLONE_URL` / `KOWA_ACCEPTANCE_KNOWLEDGE_CLONE_URL` 保留覆盖能力，可改回其他运输。

停机：`Ctrl-C`（先停 Runner，再停控制面与 Web origin）；容器保留。

## 4. GitHub App installation 可见性适配器（backend:S08 交付）

背景：S01 的冻结合同把"仓库可见性"这一外部事实留给 S08 提供（`api/identity-workspace/v1/README.md`："Real GitHub App installation and authorization are deliberately not part of S01; S08 supplies those external facts without changing this contract"）。真实组合根此前只有 fail-closed 适配器，因此真实部署连"登记双仓"都无法完成。

- 语义（`internal/githubapp`）：`KOWA_GITHUB_APP_ID` + `KOWA_GITHUB_APP_PRIVATE_KEY_PATH` → RS256 App JWT → `POST /app/installations/{id}/access_tokens` → `GET /installation/repositories`（分页、上限 20 页）→ 仓库 id 是否在 installation 可见集合内。可见 ⇒ 通过；不可见或任何读取失败 ⇒ 返回错误，S01 的 `binding()` 仍按冻结映射记为 `RESOURCE_UNAVAILABLE`（fail closed）。
- 缓存：installation token 直到到期前 5 分钟才重取；仓库列表按 installation 短 TTL（默认 60s）缓存。
- 默认行为：两个变量都未配置时，组合根保持原 fail-closed 适配器；只配置一半是启动错误（不静默回退）。合同、错误语义与 Workspace 授权均未改动。
- 凭据治理：私钥按路径读取、只在进程内使用；错误信息只含状态码与路径，不带密钥/JWT/installation token。门禁：`go test ./internal/githubapp/...`、`go test ./test/security/...`、`go test ./internal/server/ -run TestTheVisibilityPort`。
- 理由（回应研究稿"MVP 运行服务不配置 App 私钥"的顾虑）：该顾虑针对**写路径**（不签发 installation 写令牌、不用 App 身份替代个人账号写仓库）；本适配器只读、权限集为 Metadata/Contents 只读，私钥由用户持有并以仓库外路径引用，产品配置不内嵌任何密钥材料。写路径仍完全走 Runner 受控通道的个人 `gh` 身份（`doc/decision.md` 的既有决定未变）。

## 5. 场景触发与证据口径（W1—W9）

每个场景使用新的 WorkItem/Run/Task/Artifact/PR；旧运行不得作为新证据。判定口径见 [MVP 真实集成验收方案](MVP真实集成验收方案.md) §5 与 [MVP 验收矩阵](MVP验收矩阵.md) §4：

- `PASS`：新运行满足矩阵目标，身份/版本/摘要/外部事实可对账。
- `BLOCKING_FAIL`：Kowa producer/transition/consumer 违反明确合同；必须指出责任 owner。
- `OBSERVATION_ONLY`：确定性链路合法而模型/外部波动；不得吞掉规定的同步门禁失败。

每个场景最少证据集合（AI 只读采集）：WorkItem/Run/NodeRun/Task/HumanTask/Artifact 身份与水位、被测提交与知识版本、数据库查询水位、日志片段（已脱敏）、GitHub 侧实际事实（PR 号/Review/merge OID/commit author 与 committer）、命令与退出码。**不写入任何令牌、私钥、会话 cookie 或截图。**

W1 建议需求文本（沙箱仓当前 main 全绿，`fixture/failing-test` 的缺陷不在 main 上）：

> 在 `calc` 包新增 `Max(a, b int) int`（返回较大者），并补充覆盖 `Max` 的单元测试；验收标准：`go test ./...` 全部通过。
