# 测试仓库约定：SnWalker/kowa-sandbox

性质：跨端可复跑验收的环境约定；不维护阶段状态，也**不构成对任何写操作的授权**。真实 GitHub 写入仍按根 `AGENTS.md` §6 由用户执行，除非用户在当次任务中明确授权具体范围。依据与实测见 [S04 前置风险验证 Spike 报告](../research/s04-prerisk-spike-20261002.md)。最近核验：2026-10-02。

## 1. 用途与边界

`SnWalker/kowa-sandbox` 是 Kowa 整个开发与调试期间用于真实 `git`/`gh` 行为的专用测试仓库：clone、commit、工作分支 push、PR、Review/合并观测、Runner/Provider 运行。它只含一个假数据 Go 包 `calc`，一切内容可丢弃。

- Kowa 的代码、CI、文档与自动测试**不得依赖**该仓库存在或处于特定状态；它只服务于人工授权的真实验收与调试。
- 它在 MVP 里只扮演“业务项目仓库”角色。“知识库仓库（只读）”角色需要另一个仓库，见 §6。
- 不得用它存放 Kowa 证据；证据写入 Kowa 仓库的 `record/`。

## 3. 分支与标签约定

| 引用 | 用途 | 规则 |
| :--- | :--- | :--- |
| `main` | 全绿的最小基线 | 任何会话**不得**推送、强推、合并到 `main` |
| `fixture/<name>` | 可复用起点（如“修复失败测试”） | 只能从中派生；**不得**向其推送；PR 可以把它作为 base（只建 PR，不合并） |
| `baseline` | 初始提交标签 | 不移动 |
| `task/<id>` | 一次任务/执行尝试的工作分支（Runner 的工作分支） | 实验后删除；`<id>` 用任务或 spike 标识 |
| `exp/<topic>` | 一次性实验 | 实验后删除 |

命名之外的分支视为违规，应在清理时删除。

## 4. 允许与禁止的操作

在用户于当次任务中明确授权后，允许（范围以授权文本为准）：

- 从 `main` 或 `fixture/*` 派生 `task/<id>`、`exp/<topic>`；在其上提交；推送这些**非默认分支**。
- 创建、关闭 PR；删除自己创建的 `task/*`、`exp/*` 分支。

永远禁止（除非用户另行专项授权并修改本约定）：

- 向 `main` 或 `fixture/*` 推送；合并任何 PR；强推；
- 删除或改名仓库，修改仓库设置或可见性，安装/授权 GitHub App，创建 Webhook/Deploy key/Secret，修改账号级设置；
- 修改 Kowa 源仓库或其他任何仓库；
- 打印或泄露令牌、私钥内容。

注意：Coder 设计上不持有远端凭证，但同机同账号下 Agent 进程仍可读到宿主个人 gh/SSH 凭证并直接调用，沙箱仓库的“禁止”对它**没有技术约束**（报告 §5、§8）。因此每次会话前后都要做 §5 的 ref 断言，不能依赖提示词。

## 5. 会话预检与收尾（可复跑命令）

预检（只读）：

```bash
gh api repos/SnWalker/kowa-sandbox --jq '{private,visibility}'                  # 必须 private
gh api user --jq '{login,id}'                                                   # 必须 SnWalker / 135722937
gh auth status --active --json hosts                                            # login/active/state 符合预期
ssh -o BatchMode=yes -T git@github.com                                          # 必须出现 "Hi SnWalker!"（退出码 1 是正常的）
git config --get user.email                                                      # 与预期作者一致
git ls-remote origin                                                             # 期望仅有 main、fixture/failing-test、baseline
go test ./...                                                                    # main 通过；fixture/failing-test 必须失败
```

收尾（需授权）：

```bash
gh pr list --repo SnWalker/kowa-sandbox --state open --json number,headRefName
gh pr close <n> --repo SnWalker/kowa-sandbox                                     # 逐个关闭
git push origin --delete <task/* 或 exp/* 分支>                                  # 只删除本会话创建的分支
git ls-remote origin                                                             # 断言：main=d4943b0…，fixture/failing-test=0a62e29…，refs/tags/baseline=d4943b0…
```

已知残留：关闭的 PR 会保留 GitHub 隐藏引用 `refs/pull/<n>/head`，无法删除；PR 编号只增不减。

## 6. 重置方法

1. 关闭所有未关闭 PR；删除所有 `task/*`、`exp/*` 分支（§5 收尾）。
2. `main` 与 `fixture/failing-test` 若被误改，应恢复到上表 SHA：`main` → `d4943b0…`（即 `baseline`），`fixture/failing-test` → `0a62e29…`。
   - 沙箱仓库自带 README 写的是“把 main 或 fixture 还原到 `baseline` 标签的提交”。这对 `fixture/failing-test` 不成立（`baseline` 不含故障）。以本表 SHA 为准；修正沙箱 README 属于仓库内容修改，需用户执行。
   - 恢复 `main`/`fixture/*` 本身是对受保护分支的强推，**必须由用户亲自执行**。
3. 重新执行 §5 预检，确认 `go test` 结果。

## 7. 不得放置的内容

令牌、密钥、凭证、真实个人/客户数据、专有代码、大文件、生成物、Kowa 证据；GitHub Actions 工作流、Webhook、Secret、Deploy key（除非阶段明确需要，且先登记在本目录，见 §8 的“CI 观测”）；任何 Kowa 源码副本。

## 8. 后续阶段如何复用

| 阶段 | 使用方式 | 需要额外准备 |
| :--- | :--- | :--- |

### 第二个（知识库只读）仓库

需要时机：首次出现“同一任务同时物化项目仓与知识仓并断言知识仓不可写”（预计在 S04 的工作区物化/Git 证据子阶段，或 S03 之后任何需要真实知识仓的验收）。当前**不创建**。

创建前须先向用户提出，建议约定：名称 `SnWalker/kowa-sandbox-knowledge`，private，仅含假数据 Markdown 目录/索引，`main` 单分支，规则与本约定相同；创建、授权与任何设置由用户批准并执行。本约定在其创建后补充其基线与 SHA。

### CI 观测

沙箱目前没有任何 Actions；`commits/<sha>/status` 因此返回 `state:"pending", total_count:0`（“无检查”看起来像“检查中”）。S05 若要验证 CI 事实读取，需要一个最小工作流和用户批准，且须把“无检查”与“检查中”区分作为负向用例。
