=== Minimal implementation ===
1. internal/orchestration/advance.go — scopes() now attaches the write scope of the independent publish_pr step:
   {repository: project, role: project, operation: publish_pr, ref: workingBranchRef} (and nothing else changes).
2. internal/runner/git.go — the controlled channel implements the write:
   - reads the frozen working branch's remote tip with ls-remote (unreadable ⇒ git_push_unknown, fail closed);
   - fetches exactly that branch into the local remote-tracking namespace (the attempt workspace is cloned at the
     frozen baseline, so the delivered branch exists only on the remote; the fetch makes the head resolvable for the
     pull request tooling and re-verifies the remote tip at the moment of the write);
   - derives the GitHub owner/name slug from the registered clone URL and the protected delivery branch from the
     main|master convention (a repository without either is refused);
   - lists open pull requests for that head and, when one exists, reuses it (a retried attempt never opens a second
     object); otherwise runs the controlled `gh pr create` with the machine's own identity, and reconciles a failed
     create against GitHub before reporting anything;
   - reads the object back with `gh pr view` and refuses to report unless it is OPEN, based on the protected branch,
     headed at the delivered tip and authored by the frozen machine identity;
   - returns the delivery record extended with pullRequestNumber/pullRequestUrl and records every command in the
     attempt's delivery evidence (git config/ls-remote + gh list/create/view); gh runs through the same injectable
     process runner as git, with the worker environment allowlist and the attempt log directory.
3. internal/runner/scopes.go — the delivery record's pull request fields flow into outcome.Output["delivery"] and the
   top-level pr_number the capability declares; the control plane still settles the operation by observing GitHub.

=== Boundaries and known limits (recorded, not hidden) ===
- Real positive case (an actual pull request on SnWalker/kowa-sandbox) is left to the new W1 run per the approved plan;
  no real PR is created by this session's tests.
- The App is not involved: PR creation uses the machine's personal gh identity (scopes include repo); no App permission
  change is needed (checked against the App's read-only contents/metadata permissions and the login-only role).
- A revised delivery pushes a new commit to the same run branch; GitHub allows only one open PR per head branch, so a
  second publish for the same branch reuses (not duplicates) the first PR. The flow's revision path (S06 rerun
  semantics) is therefore only exercised end-to-end by a W1 revision scenario, which this stage has not run yet.
- Same-account reality unchanged: the worker process could still reach the host's gh credentials; the prompt forbids
  remote operations, the channel's idempotent reuse keeps any such attempt coherent, and the design's acknowledged
  non-hard-isolation boundary stands.
