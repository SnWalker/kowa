## 1. 项目定位

### 1.1 要解决的问题

Kowa 是面向 GitHub 的 Coding Agent 研发工作流编排平台，将自然语言研发需求转化为可执行、可观察、可审计和可恢复的工作流，解决复杂需求拆解、多仓库协作、独立评审、跨机器交接、人工门禁和持续评测缺少统一治理的问题。

流程与状态由控制面持有，具体任务由分布式执行面完成；正确性不得依赖同一机器、同一 Agent 会话或不可重建的本地状态。

### 1.2 目标用户

主要用户是使用 GitHub 协作并希望把 Coding Agent 纳入正式研发流程的研发团队、项目 Owner、技术负责人、质量与安全角色及平台工程团队；能力开发者可以接入新的 Agent、工具和外部平台。

### 1.3 核心价值与场景

- 以显式工作项、契约、依赖和汇合条件组织单仓与多仓研发。
- 以独立角色、隔离上下文和结构化交接完成方案、编码、测试、评审、安全审计与 PR 交付。
- 以中心真源、冻结输入、版本化产物、人工控制和评测闭环保证可追溯、可恢复与可复现。
- 支持多 Runner、多 Provider、父子工作项、失败恢复、局部重跑、隔离回放和持续评测。

### 1.4 非目标

Kowa 不替代 GitHub、CI/CD、制品存储和可观测平台，也不以无人负责的全自动交付为目标；首期不建设通用 BPM 或完整项目管理套件，不依赖 Agent 互聊、共享隐式会话或跨机器本地目录完成交接。

### 1.5 首期 MVP 范围

Kowa 优先参考历史项目的核心流程和设计，在 GitHub 场景下复现并验证；历史项目仍是设计参考，不是可直接继承的完整实现基线。

首期以已有项目仓库中的小型功能或缺陷修复为验收场景。Workspace 登记业务项目仓库和配套知识库仓库，每个工作项只写一个业务项目仓库；知识库在运行期间只读。知识绑定是显式起始步骤：系统推荐条目，用户增删并确认后冻结知识版本。首期使用明确目录或索引，不以向量检索为前提。

首期面向一个小团队的多人使用。成员以各自 GitHub 用户身份登录，Kowa 的 Workspace 成员资格和处理人工任务的权限由服务端授权，不因安装 GitHub App 或登录成功自动取得管理员权限。

首期只交付一条固定、内置、版本化且经校验和冻结的工作流。用户通过 Web 输入需求、配置参数、查看真实 DAG 和处理人工任务；不实现多模板选择或任意 DAG 编辑器。定义与能力分离，后续新增工作流能够复用已有能力，已有工作流能够通过新定义版本增加 Agent 节点，不能改变既有运行的冻结定义。交付闭环包含知识绑定、方案与独立评审、人工批准、编码与验证、独立代码评审、PR 人工批准与合并、集成验证和关闭。

首期实现历史查看、Retry、受控返修与必要的 Rerun；Replay 操作功能、多仓父子编排、D2C 和部署预览延后。冻结定义、版本化输入输出与证据必须从首期保留，不以延后 Replay 为由省略。

## 2. 核心术语与领域模型

核心对象链为 `Workspace → WorkItem → WorkflowRun → NodeRun → Task / HumanTask → Artifact / Evidence`。Workflow 定义过程，WorkflowRun 执行冻结定义；NodeRun 表示逻辑节点，Task 表示执行面的实际执行尝试，各层不得因界面或外部平台的数据结构而合并。

### 2.1 Workspace

团队或项目的长期协作、权限与资源边界，登记 GitHub 仓库、知识源、工作流、Runner、Capability、Provider 和治理策略；它不等同于执行机目录，本地内容只是可重建投影。

### 2.2 WorkItem 与父子工作项

WorkItem 表示一项研发目标，承载需求、范围、验收标准、依赖和交付结果。复杂需求由父 WorkItem 拆解、协调和汇合；每个子 WorkItem 恰好绑定一个可写目标仓库，依赖仓库只能按冻结版本只读消费，任何第二个可写仓库都必须继续拆分。

首期关闭以人工批准合并及集成验证通过为条件。已关闭工作项不重开，后续修改创建关联的新工作项；合并后验证失败时原工作项保持未完成，需要改代码则经人工确认在同一工作项下开启修复运行和新 PR，不自动回滚。

### 2.3 Workflow、WorkflowRun 与 NodeRun

Workflow 是版本化的声明式流程定义，经校验、编译和冻结后运行；WorkflowRun 是针对 WorkItem 或其他明确主体的一次执行实例；NodeRun 是其中一个逻辑节点的状态、有效输入、结构化输出、产物与证据记录。

### 2.4 Runtime、Runner、Worker、Capability、Provider 与 Task

- **执行面**：所有 Runner 及其 Worker、Capability Adapter、隔离工作区和外部工具的总称；控制面不执行 Agent 任务。
- **Runtime**：控制面对在线执行环境的逻辑登记；**Runner**：承载该环境、准备工作区、监管执行并上报结果的实际宿主进程。
- **Worker** 实现具体 **Capability**；Capability 是稳定、可版本化的调度契约；**Provider** 是 Worker 调用的 Coding Agent、模型或工具供应方，Adapter 负责协议转换。
- **Task**：控制面派发给执行面的最小可租约执行记录，关联一个 NodeRun；重试、续接或重新分派不会混淆 Task、NodeRun 与 WorkflowRun。

每次真实重新执行创建新 Task，重复投递同一次执行复用原 Task。Retry 保持有效输入；人工续接关联已接受的新答复和前一次 Task。Provider 会话仅是可选执行优化，不替代任务身份与持久化事实。

### 2.5 HumanTask 与人工门禁

HumanTask 统一表示所有等待用户确认、选择、补充输入或执行真实操作的持久化任务；人工门禁阻止相关节点和下游继续。Web 与后续渠道 Adapter 只渲染和提交同一份服务端定义。

### 2.6 Artifact、Evidence 与 Context

Artifact 是可寻址、可版本化和可校验的输入或输出；Evidence 是支持执行或验收结论的可验证事实；Context 由需求、知识、上游输出、契约、策略和人工输入显式组装，不包含隐式聊天记忆或偶然本地文件。

### 2.7 Repository、Branch、Worktree 与变更集

Repository 与 Branch 的远端事实由 GitHub 持有；Worktree 是 Runner 准备的隔离、可重建本地投影；变更集绑定仓库、基线、目标版本和内容摘要。代码变更的跨机器交接必须使用 GitHub 稳定引用，非代码制品通过 Artifact Store 交接。

已发布代码供工作流下游跨机器消费时，以 GitHub 的固定提交为正式引用。Runner 在冻结的仓库身份和基线下物化项目与知识仓；Coder 在获准的项目工作分支上以 Runner 本机 GitHub 身份提交、推送并报告远端提交引用。QA、评审和后续节点按该引用重建输入，不依赖 Coder 本地目录或可变的分支最新值。

### 2.8 Contract、IDL 契约与渲染契约

Contract 必须有唯一 Owner、Producer、Consumer 和版本。跨仓接口以独立 IDL/协议仓库为真源并先形成冻结契约；渲染契约约束 Web 实际消费的字段与交互语义，但不能替代 IDL。

### 2.9 History View、Retry、Rerun 与 Replay

- **History View**：只读展示历史运行，不执行节点或创建新运行。
- **Retry**：节点因执行错误、超时或基础设施故障未完成时，以相同有效输入再次尝试。
- **Rerun**：在当前 WorkflowRun 中重新执行指定节点及受影响下游，产生新结果和产物版本。
- **Replay**：以历史运行的不可变快照创建隔离运行；复用未选节点的冻结结果，只真实执行选中节点，不修改源运行。

## 3. 架构边界

### 3.1 控制面与执行面

控制面负责编排、状态持久化、调度、权限、人工交互和审计；执行面负责声明能力、接收任务、执行并上报进度、结果与心跳。首期采用模块化单体控制面与独立 Runner，出现真实扩展压力后再拆分部署单元。

MVP 首先部署一个 Runner，保留任务协议、租约校验和持久产物交接，并验证无共享执行目录的接力；多 Runner 调度优化和高可用后置。单 Runner 部署不改变跨机器可恢复的正确性约束。

### 3.2 状态与制品真源

PostgreSQL 保存工作流与任务状态真源，GitHub 保存代码、提交和 PR 真源，Artifact Store 保存可寻址的非代码制品与证据；本地仓库、Worktree 和运行目录都是可重建投影。

### 3.3 平台与适配器

首期用户入口仅实现 Web，飞书等渠道后续通过 Adapter 接入；GitHub 通过 GitHub App 集成。Claude Code、Codex 等 Coding Agent 共享统一任务与结果协议，核心领域只依赖 Kowa 定义的稳定端口。

首期 Web 通过 GitHub App 用户授权登录，Kowa 建立服务端会话并独立判断 Workspace、WorkItem 与人工任务权限。MVP 的 GitHub 远端代码操作由获准 Task 在 Runner 执行面使用该机器预先登录的个人 `gh`/Git 凭证完成；Coding Agent 可以在任务工作区执行本地 Git 和项目仓远端 Git 操作。必需测试及独立评审通过后，独立 `publish_pr` 节点使用同一机器身份创建 PR。GitHub 记录的 push 操作者、commit author/committer 与 PR 创建者是 Runner 机器的个人 GitHub 账号，Web 发起人和 Agent 生成来源由 Kowa 分别记录，不冒称 GitHub 写入属于 Web 发起人。PR 由有权真人且非 PR 作者提交有效 Review，合并仍由人在 GitHub 执行；Kowa 核对当前提交、Review、合并事实及合并后验证。

首期 Runner 在本机 Mac 调用该机器已安装、可用的 Claude Code、Codex 等 Provider CLI；团队成员共用这些本机执行能力。Runner 登记实际可用能力与版本，Kowa 为每次任务分别记录发起人和执行证据。后续跨机器运行不能依赖某台 Mac 的个人主目录作为任务输入或交付真源。

### 3.4 技术栈基线

- 版本优先选择经验证的成熟版本并明确固定；同一版本线内的修复升级须验证，跨主要版本或改变兼容性的升级须重新确认共识。
- 控制面与 Runner 使用 Go 1.25.14。
- 后端采用标准 `net/http`、Uber Fx 和分层架构；Fx 用于组装与生命周期，领域规则不依赖框架。关系字段与 JSONB 按数据职责分工，关键状态和关联不能隐藏在无约束 JSON 中。
- Web UI 使用 Node.js 22.23.2、pnpm 10.34.5、React 18.3.1、TypeScript 5.9.3。
- 持久化使用 PostgreSQL 17.11。
- 本地工具链由 `mise.toml` 管理，不替换全局工具版本；CI 与容器独立固定相同版本；全局安装的 Codex、Claude Code 等工具不由项目级 mise 管理。
- 浏览器与控制面使用 HTTP 和事件流；Runner 采用出站连接完成注册、任务接收、心跳和结果上报。MVP 使用出站 HTTP 长轮询获取任务，配合 HTTP 心跳和结果上报；连接不承担状态真源，后续可在同一业务契约下替换传输。
- Artifact Store 开发环境可使用本地文件系统，生产环境使用兼容 S3 的对象存储。
- 核心编排不预先绑定 Redis、Kafka、Temporal；外部子系统的必要依赖单独登记，不能由此推断整个部署不含这些组件。其他依赖版本由实现基线冻结。

## 4. 关键不变量

- 工作流定义经校验、编译和版本冻结后运行，运行期间不得漂移。
- 一个业务决定只能有一个权威；投影可以转换形状，但不得重新解释业务语义。
- 中心状态是真源；同机是优化，跨机可恢复是正确性要求。
- 节点只通过结构化结果、显式 Context 和可校验制品交接，不依赖隐式会话或本地绝对路径。
- 确定性规则优先于模型判断；人工决策必须显式建模并持久化。
- Planner、Coder、Reviewer、Security Reviewer、QA 与 Evaluator 保持职责和证据隔离，可使用不同模型交叉评审。
- 跨仓需求按仓库拆分子 WorkItem；跨仓接口必须有独立 IDL/协议契约 Producer，Consumer 不得自行重定义契约。
- 默认最小权限；高风险操作需要人工授权；外部系统只通过稳定端口与 Adapter 接入。
- 不长期保留兼容 facade、双写模型、旧字段或旧消费者；阶段性过渡必须在退出前清理。

## 5. 长期约束

### 5.1 工作流与协作

需求进入后依次形成知识与上下文、方案、评审、人工批准、拆解与依赖、编码、验证、独立评审、发布请求、集成验收和关闭；允许显式并行、循环、暂停、取消与恢复。父工作项只在子项满足汇合条件后继续。

自动评审返修有明确预算，耗尽后转人工处置，不能自动视为通过；确定性必需验证失败仍阻断交付。

### 5.2 分布式执行与交接

Runner 通过注册、能力发现、任务租约、心跳和过期租约写回隔离接受调度；仓库和知识按冻结版本物化。进度只上报控制面，代码变更通过 GitHub 稳定引用交接，非代码产物通过 Artifact Store 交接。

### 5.3 上下文与知识

需求上下文、Workspace 知识、工作项 Dossier 和运行上下文必须标注版本、来源与可信度；知识绑定与回灌受人工确认和明确权威约束，不能把搜索结果或模型记忆直接提升为事实。

MVP 的知识回灌只生成更新建议 Artifact，不自动修改或合并知识库。建议生成失败保留失败与待处理记录、支持后续重试，不阻止已经满足必需条件的业务交付关闭。

### 5.4 评测与质量

Kowa 评测结果、过程与工作流三层质量，结合确定性检查、模型评审和人工校准，并跟踪成本、延迟、干预率与恢复能力。交付契约明确要求的质量与安全评测属于同步门禁；离线回归、统计和持续校准异步执行，不反向改变已完成的研发交付状态。

Kowa 持有评测领域和数据闭环；首期接入自托管 Langfuse，使用 OpenTelemetry 传递轨迹。Langfuse 不拥有工作流状态，Prompt 的源码、审批和发布仍以 GitHub PR 为真源，评测后端通过可替换端口接入。

### 5.5 安全、体验与非功能目标

系统必须落实身份与权限、仓库与分支保护、凭证和敏感信息治理、工具与网络策略、供应链和生成代码安全。用户应看到进度、阻塞、人工任务、证据和交付结果；系统必须诚实表达失败与不确定性，并持续满足正确性、可恢复性、可观测性、可审计性、可替换性和可测试性。
