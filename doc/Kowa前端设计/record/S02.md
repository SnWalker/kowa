#### 执行结果

- 首个红灯：见上（fixture 双未覆盖 S02 操作 → `unmapped fixture request`）；真实控制面首次扩展后亦按"控制面缺受控仓库/registry"路径暴露真实失败，驱动 harness 扩展（见下）。
- 实际根因或设计发现：
  1. 旧准入块的两条 `application` 死条目与 main 不一致（规划漏项 + 文档漂移）。
  2. 知识确认的 `required` 语义、`decision` 必需字段与"答复对象版本必须取自 `human.detail`"由 producer 决定，前端不得自建规则。
  3. **答复接受与知识冻结解耦（`CODE_CONFIRMED`）**：`human.response` 只收下任务答复（200 `RESOLVED` + 续接意图），冻结由 backend:S06 消费续接意图时执行。因此（a）答复被接受后绑定不会立即出现——前端以有界的运行投影重读观察真实转换，读不到就不显示为已确认；（b）丢弃 `required` 或含索引外路径的答复**不会**以 422 拒绝答复本身，而是任务 `RESOLVED` 后拒绝冻结绑定（零快照、零派发、运行留在等待）；只读预检 §6 的"422 呈现"预期与真实 producer 行为不一致，本阶段以真实行为为准并在此登记。
  4. **真实控制面下"启动版本冲突"的语义是"该工作项已有推进运行"**：重取投影后启动入口被运行视图取代（服务端一工作项一推进运行），因此把拒绝说明上提到工作项级、保留在运行视图上方（`src/workitems/WorkItemDetailPage.tsx`）；fixture 层仍保留"显式确认后重提"的分支机制并用组件测试覆盖。
  5. **派发断言必须按运行归属**：脚本化 Runtime 的租约队列按运行时（跨工作区）共享，因此 E2E 的"零派发/已派发"断言以任务 id 是否属于被测运行判定（`tests/e2e/support/journey.ts` 的 `taskOfRun`/`expectNoRunTask`/`leaseRunTask`）。
- 发现分类与原冻结承诺：规划漏项（G1/G2/G3 的补登与替换）+ 文档漂移（依赖声明收敛）+ 预检推断偏差（3、4 项的期望与真实 producer 不同）+ 前序窄化（`EXTERNAL_UNKNOWN`）；无任何后端 DONE 阶段的原冻结承诺被违反（"索引内增删/确认、`required` 不可删、索引外一律拒绝"与"冻结输入不可漂移"均由真实 producer 保持），未触发重开。

## 记录约束

- 计划记录"准备怎么做"，record 记录"实际发生了什么"；两者不要求完全一致。
- 按真实时间追加，不重写失败、偏差、假绿色或被推翻的证据。

- 真实操作前记录版本、水位、目标对象和预期数量；操作后优先使用用户返回的 ID，只能通过只读方式验收。

- Record 可以记录状态变化历史，但不得成为实时状态权威。
