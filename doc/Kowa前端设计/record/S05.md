#### 执行结果

- **数据通路**：新增 `src/humantasks/`（`presentation.ts` 纯语义、`HumanTasksPage`、`HumanTaskDetailPage`、`HumanTaskAnswer`、`HumanTaskBasis`）与 `src/runs/RecoverySection.tsx` + `src/runs/recovery.ts`（纯候选推导）。待办列表/详情只读 `human.list`/`human.detail`；详情页的三个依据读取（运行投影、冻结定义、已发布产物）各自独立失败、互不清空；恢复区只读运行投影与工作项投影，写入只有 `run.recovery` 一条通道。
- **所审版本与不改绑（本阶段核心语义）**：答复载荷逐字取自 `human.detail` 的 `request.version` 与 `request.object`（kind/id/version/digest），页面从不从知识推荐或产物清单重建对象版本；详情页把「页面读到的投影摘要」与「所审版本」并排显示为一致/不一致/未知三态，未知不写成一致；`EXPIRED` 一律引导重新审阅并写明不会自动重试、不会改绑。
- **通用动态表单**：按冻结字段类型映射控件（`decision`→单选组、`text`→输入、`choice`→下拉、`comment`→文本域），值一律从空开始（预填即代答，服务端也冻结了"预填不构成确认"）；`answerValues` 逐项复刻 owner 的校验（只接受声明字段、必填非空、choice 在登记选项内、顶层 decision 与字段一致），任何一项不满足就不提供提交入口；`human.list`/`human.detail` 的 `availableActions` 是唯一动作权威，空数组时页面写明"服务端没有为当前身份返回 respond 动作"。
- **依据阅读**：知识确认的依据是运行投影里的冻结索引（含逐条 path/scope/digest/required），并核对 `indexDigest` 是否等于所审版本；方案审批的依据是已发布产物清单里摘要等于所审版本的条目（契约不提供浏览器端内容读取，页面如实说明并无下载链接）；返修升级的依据是冻结定义中该节点的自动返修预算（`maxAutoRevisions`/`targetNodeId`）与目标节点已记录轮次；外部事实的依据只有对象绑定（PR 号 + head OID）。对象类别没有浏览器读取操作时，页面明写"没有该对象的读取操作"，不构造替代视图。
- **恢复交互（候选语义）**：`run.recovery` 没有动作清单投影，因此 `src/runs/recovery.ts` 按服务端已记录事实逐条给出**候选**并注明「是否接受由服务端裁决」：每个候选都带 `basis`（服务端投影中的哪一条）、`versionGuard`（owner 实际校验哪个版本）、`reasonRequired`，事实不存在时不提供控件并写明缺哪条事实。页面在加载与重读时零写入；提交按意图复用请求键（重复点击或传输失败重发在服务端是一次幂等命令）；`applied` 与 `detail` 原样呈现，`applied=false` 写成「命令未被应用」；版本冲突按该命令自己的守卫报告版本（`cancel`→运行版本、`repair`→工作项版本）并重读对应投影，等待显式重发。
- **本轮关键实现发现（按发现顺序）**：
  0. **恢复命令没有服务端动作清单（`CODE_CONFIRMED`，契约边界）**：`RunDetail`/`RecoveryRequest` 都不含 `availableActions`，与人工请求不同。因此本阶段的恢复区不能声称"已获授权"，只能按服务端事实给出候选并写明由服务端裁决；真实控制面 E2E 用陈旧版本证明该守卫确实存在（见"真实控制面结果"）。这是把"允许动作来自服务端"落到没有动作清单的载体上的唯一诚实做法，已写进阶段文件与准入证据。
  1. **阶段文件的第一条 `requires` 是死条目（`CODE_CONFIRMED`）**：`backend:S02 run.recovery-core` 的 manifest 不存在且自标 `application`，已按 S02/S04 先例勘误移除并收敛依赖声明。
  2. **字段类型是闭集，未知类型到不了页面（`CODE_CONFIRMED`）**：目标红线原设想的"未知字段"在解码层就被拒绝（enum + `asExactObject`），因此组件级红线改为唯一可达形态——`choice` 无 `options`：页面不画控件、不提供提交入口、并给出原因；`human-task-presentation.test.ts` 第 109 行仍保留对伪造未知类型的防御性单测，但它是对 helper 的防御，不是可达路径（已在测试注释中写明）。
  3. **提交按钮被禁用时的原因文案曾把两件事说成一件事（`CODE_CONFIRMED`，表现层缺陷）**：初版 `answerValues` 先判"顶层 decision 与字段 decision 不一致"，于是"还没选"也被报成"不一致"。改为先判必填缺失再判一致性（E2E 首轮即暴露该文案，见 `s05-human-task-detail-light.png` 之后的修复轮）。
  4. **版本冲突必须按命令自己的守卫报告（`CODE_CONFIRMED`，正确性）**：`repair` 校验工作项版本、`cancel` 校验运行版本，初版冲突提示一律显示运行版本，会在 `repair` 上报错对象（真实工作项的 409 会显示成运行的版本）。改为按 `versionGuard` 选择重读对象与展示版本，并补单测锁定（"服务端工作项当前为 v4"）。
  5. **恢复控件在依据不足时不应渲染（`CODE_CONFIRMED`，UX/诚实性）**：初版把不可用候选渲染为禁用按钮，读起来像"只是暂时点不了"；改为不渲染控件并写明缺少哪条事实，单测断言此时不存在该按钮。
  6. **控制面测试基座的运行凭据按引擎登记（`CODE_CONFIRMED`，测试基座）**：`tests/webharness/main.go` 把 token 绑定到唯一 runtime id，本阶段按 S02/S04 先例追加 `{id}-{engine}-s05`（`git log -S '"-s04"' -- tests/webharness/main.go` 指向 S04 阶段提交），未改动其他凭据。
  7. **焦点与错误关联（`CODE_CONFIRMED`，可访问性）**：拒绝或冲突时焦点落到结果块（`tabIndex=-1` 的容器），错误以 `role="alert"` 播报、等待类以 `role="status"`；单测断言拒绝后焦点所在元素确实带着拒绝类别。
- 发现分类与原冻结承诺：本阶段未发现后端 `DONE` 阶段的原冻结承诺被违反。8 项发现分别为准入勘误（1）、契约边界事实（0、2）、表现层/正确性缺陷（3、4、5）、测试基座缺口（6）与可访问性实现（7）。**无 `BLOCKING_FAIL`**。
