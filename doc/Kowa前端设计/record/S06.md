#### 执行结果

- **数据通路**：新增 `src/delivery/`（`presentation.ts` 纯语义、`DeliverySection.tsx` 容器与身份/操作/事实/水位/证据区、`ClosurePanel.tsx` 关闭记录与清单及运行谱系、`links.ts` 外链策略、`GitHubLink.tsx` 链接原子）。交付证据区一次工作项级读取 + 三个独立读取（运行身份、已发布产物、观察水位），每个失败各自独立、互不清空；页面**没有**任何写操作。
- **身份分层（本阶段核心语义）**：`identityLayers` 逐层绑定到它真正来自的字段（`run.detail-history.startedByGitHubUserId`、`gitExecutionUserId`，`delivery.query.operations[].request.expectedGitHubUserId`、`...result.pullRequestAuthorId`、`...result.observedByGitHubUserId`），各自独立成行；「远端 commit author / committer」一层显式写明**任何已冻结的浏览器消费合同都不携带它**（`grep` 证据见「开工事实」），并说明 GitHub 认证操作者不能从姓名文本反推、远端写入的认证操作者以机器账号与 PR 作者为准。运行视图原来的「Web 发起人 / Runner 机器身份」一行拆成两行（`C05`：两者是不同身份）。
- **冲突与不放行**：`identityConflicts` 判定 PR 作者≠准入机器账号、对账提交≠请求提交、对账 ref≠请求 ref、操作账号≠运行冻结算号四类，任一出现即以 `Notice tone="warning"` 逐条列出并写明服务端以这些事实为准。
- **PR / Review / merge / CI 事实**：PR 观察显示编号（含 GitHub 链接）、状态、head、作者、源/目标 ref 与合并事实（合并提交 + 合并账号 + 账号类型 + 时间），并写明「账号类型是 GitHub 的事实，不证明人亲自操作，Kowa 也不推定」；Review 观察把**处理人（登录名 + 数字 ID）、账号类型、仓库权限、关联、结论**与**适用提交**分两个数据块呈现，适用性只有 `适用于当前 head` / `不适用于当前 head` / `适用提交未知` 三态；checks 四态各自带文字说明，`none` 明写「不是通过」。
- **外部未知**：失败的读取单独成块（观察 ID、尝试时间、原因、以及「这次读取没有给出事实」），绝不出现在事实列表里；「最后成功观察（本投影）」取成功读取中最新的一条 `observedAt`，并写明界面重连或 SSE 不断开都不代表 GitHub 状态更新。
- **观察水位**：消费 owner 自己的 `observability.watermarks`，逐主体显示 `lastAttemptAt`/`lastAttemptKnown`/`freshness`(+`freshnessReason`)，并写明「最后成功读取时间不在这条水位里，本页不外推」；新鲜窗口用服务端给出的 `freshnessWindowSeconds`，页面不设第二套阈值。
- **质量证据**：按 owner 的分组把四个同步门禁与两个辅助事实分开；`simulated` 来源一律不读作通过；每条显示被验证对象、来源、生产者、配置版本与报告产物引用（在已发布产物清单里核对种类/媒体类型/状态；产物不在清单或清单读取失败时如实说明，且明写契约不提供内容读取）；辅助事实失败时给出「不阻塞关闭」并指向运行视图的 `retry-knowledge-suggestion`。
- **关闭与修复关联**：`closure` 缺席且工作项未关闭时，若已观察到合并则同时给出「已报告合并」与「未关闭」并写明合并事实与未关闭同时可见；有关闭记录时逐项重读（需求摘要、冻结定义、交付运行、必需测试、独立评审证据、有效 Review、实际合并、合并后验证），三态为「重读一致 / 重读不一致 / 本投影无法重读」，并在结尾列出未一致项；运行谱系把交付运行与修复运行分开，写明「本页不创建新运行，也不回滚任何已发生的远端事实」。
- **外链安全**：`githubRepositorySlug` 只接受 GitHub 自己的 `owner/repo` 形状且排除 `.git` 结尾；`projectLink` 还要求工作区登记的项目仓数字 ID 与本工作项目标仓库一致；任一不满足即完全不渲染 `github.com` 链接并写明原因。链接固定 `https://github.com/<slug>/{pull,commit}/<encoded>`、`target="_blank"`、`rel="noreferrer noopener"`，可访问名带「（在 GitHub 新标签页打开）」。
- **本轮关键实现发现（按发现顺序）**：
  0. **交付证据区的读取必须把 `currentRunId` 当依赖（`CODE_CONFIRMED`，正确性）**：初版依赖只有 `[workspaceId, workItemId, generation]`，于是「创建 → 启动运行」之后面板仍显示启动前那次读取的结果（“还没有外部操作”），而服务端此时已有运行。三引擎 E2E 首轮把这个缺陷直接暴露出来。改为把 `currentRunId` 纳入依赖后，准入运行会让面板重新读取。
  1. **共享 `Notice` 的标题是 `<h2>`，嵌套小标题必须格外小心（`CODE_CONFIRMED`，可访问性）**：交付证据区里嵌了多个 `Notice`（合并未关闭、未知读取、辅助失败…），它们各自在正文深处插入一个 `<h2>`；原来我把「运行与修复关联」写作 `<h4>`，axe 立即报 `heading-order`（h2 → h4 跳级）。处理：本面板内部所有小标题统一保持 `<h3>`（h2 ↔ h3 之间任何插入都不会跳级），并在代码注释里写明原因。
  2. **`Observation.actorId` 是可选的（`CODE_CONFIRMED`，契约边界）**：Go 结构体上带 `omitempty`，schema 也不在 `required` 里，因此「谁读的」可以合法缺席；解码器按可选处理，页面写成「服务端未登记」而不是凭空补一个账号。
  3. **`JourneyView.closure` 是无约束对象（`CODE_CONFIRMED`，规划漏项）**：冻结合同里该字段是 `{"type":"object"}`，生产端填的是完整 `evaluation.ClosureRecord`。消费它会形成第二个未校验的关闭权威，故不准入；backend:S06 的重排前消费者预检把 `journey` 登记给 frontend:S06，那是按旧编号的判断，本阶段按实际消费重新判定并记录在准入证据 §2.5。
  4. **observability 的 `SafeText` 需要解码器同样拒绝凭证形状（`CODE_CONFIRMED`，安全）**：schema 用 `not.pattern` 拒绝凭证样式；解码器若不重复这条规则，一个被污染的 `unknownReason` 会被原样渲染成「诊断原因」。`decodeWatermarkView` 现已按同一模式拒绝并补了负例测试。
  5. **fixture 的「显式 `undefined`」会被 schema 拒绝（`CODE_CONFIRMED`，测试基座）**：`{...base, ...overrides}` 会把 `commitOid: undefined` 变成一个**存在但为 undefined** 的键，冻结 schema 判它类型不符。本阶段的 fixture 构造器统一用 `withoutUndefined` 丢弃这些键（与 `JSON.stringify` 一致），未放宽任何 schema 校验。
