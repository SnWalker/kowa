# Workflow 与 Capability 扩展设计

状态：技术方案；单条固定流程、尝试身份、出站长轮询基线已批准。MVP 的 Agent 原生本机 Git/gh 与独立 Runner `publish_pr` 节点已选；提前 PR 不做专项硬限制，实际隔离及 schema 待审。非可执行教程。更新：2026-09-27。

本方案依据用户提供的三篇指南及其[核对记录](historical-guides-assessment.md)。它延续历史的声明式定义、统一运行器和能力协议，按 [common](../common.md) 的内置 MVP、Runner 出站和显式交接要求适配。

## 1. 四个独立扩展点

| 扩展 | 改变什么 | 不应因此改变什么 |
| :--- | :--- | :--- |
| 新 Workflow | 已有节点与能力的组合、依赖、绑定和门禁 | 通用调度器、执行协议 |
| 新 Capability | 一项稳定的输入输出与业务执行行为 | 工作项状态机、Web 私有推进逻辑 |
| 新 Provider Adapter | 已有能力如何调用模型/CLI | 能力对消费者的业务结果语义 |
| 新节点语义 | 编排器真正缺少的通用控制行为 | 不能只是新业务名称就新增 NodeType |

“新增 Agent”首先判断属于哪一类。Worker 实现 Capability，Runner 监管 Worker；不把角色、能力、Provider 和进程等同。确定性能力不必有 Prompt；同一 Runner 上的独立评审也必须隔离上下文和写权限，不能仅靠换角色名。

## 2. Workflow 发布与选择

建议首期采用仓库内版本化 YAML 作为作者输入；发布后的内置定义注册表是运行选择入口，不实现历史 project/global 本地覆盖层，也不提供任意 workflow_key 旁路。

发布身份建议由定义名和版本唯一确定，内容摘要作为其不可变值；同名同版本不同内容拒绝冲突，不把 digest 加进唯一键后允许同版本并存。MVP 只有一条固定流程，界面不提供多模板选择；后续新流程复用已有能力，已有流程以新定义版本增加 Agent 节点。扩展不能改写既有运行。未知 kind/name/version 明确报错，不回退到 bug-fix 或其他流程。

新增仅复用既有 NodeType/Capability、已有选择入口的 Workflow，主要改变定义及其测试；如果需要新能力、入口或控制语义，必须同时完成对应扩展，不能许诺只改 YAML 就足够。

用户已明确单条固定流程及两种后续扩展边界，见 [正式执行边界](../wiki/architecture/workflow-execution.md)。YAML 作者格式、仅内置加载的具体实现和上述唯一性 schema 仍为技术建议；不声称历史 loader 的行为已由缺失源码验证。

## 3. 加载、编译与冻结

| 层次 | 要做的校验 | 失败处理 |
| :--- | :--- | :--- |
| Parse | 名称/版本、节点 ID 唯一、合法字段与节点类别、必需值、资源声明 | 定义不可发布；未知字段避免静默吞掉拼写错误 |
| Compile | 依赖存在、普通依赖图无环、输入来自合法祖先、类型/可选性、条件与门禁、返修边界 | 产生定位到节点/字段的错误，禁止生成可运行定义 |
| 发布校验 | 能力目录版本存在，执行器支持，冻结配置可解析 | 内置必需定义无效则发布/启动失败 |
| 运行准入 | Workspace 授权、仓库/知识基线、实际执行环境与 Provider | 配置无效拒绝启动；临时离线显式等待，不冒充定义错误 |
| 结果接受 | 当前任务/租约、输入轮次、结果 schema、产物就绪 | 不推进 DAG，保留结构化原因 |

编译产物建议包含规范化定义、拓扑与依赖索引、输入绑定计划、受限条件、返修区域、能力/schema/Prompt 引用及摘要。WorkflowRun 持有不可变冻结版本，不在恢复时重新读取最新 YAML、catalog 或 Prompt。

冻结逻辑引用与策略，不冻结 bearer token、临时 URL 或机器绝对路径。实际 Runtime、Provider/模型版本及执行工具版本进入尝试证据。注册能力的新版本不能静默替换既有运行的冻结依赖。

## 4. 节点和输入绑定

保留历史 type、depends_on、inputs_from 的职责区分，但不照搬全部 15 类节点和旧别名。MVP 所需语义只有：能力执行、结果判断/有界返修、人工任务、控制面持久化/状态操作、依赖汇合与结束；准确枚举与 YAML 字段在合同评审时冻结。

能力执行走 Runner。控制面原生节点只能做自身用例与状态转换，不能用 in-house 白名单绕开执行面执行模型、仓库测试或任意 shell。MVP 中 Coder 使用 Runner 本机 Git/gh 完成工作分支 Git 操作；控制面决定 Task、仓库和流程准入并核对远端事实。PR 创建由测试/评审之后的独立 Runner `publish_pr` Capability 执行，不由 Server system 节点或 Coder 节点正常路径完成。

inputs_from 绑定的是声明输出路径及其 schema，不是拼接 Prompt 文本。引用必须来自传递祖先；祖先可能因条件跳过时，消费者必须明确可选或有合法分支，否则编译拒绝。运行中必需输出缺失或类型错误不能转为空值。

条件建议使用受限的纯表达式：无文件/网络/脚本副作用，缺字段和类型错误是错误而非 false。运行时按绑定计划解析到明确 node_run_id/输出版本，不能读取无版本“最新结果”。

## 5. 跳过、Join 与返修

- 条件为假、人工省略、上游失败造成的未执行分别记录原因，不将所有 skipped 视为成功。
- 必需质量门禁不可通过 non_gating、non_blocking 或宽松 trigger_rule 绕过。
- all_done 只能用于允许失败后仍执行的收尾/报告，不能单凭依赖终态触发交付成功。
- 普通依赖图保持 DAG；返修是编译后明确的有界控制转换，不是任意环。loop body 必须是已知、受影响范围可计算的区域。
- 初次评审后最多三次自动修订是当前产品口径；不能直接把历史 loop_max_iter=3 的未核实运行语义搬过来。
- 返修/人工拒绝指向的节点必须存在且被允许重入；已经发生的合并、发布等副作用不能作为普通循环体无条件重放。
- 触发返修前收束受影响的在飞任务，保留旧结果，更新消费/审批有效性，建立新轮次。

## 6. 能力目录与在线执行环境

静态 CapabilityCatalog 说明“允许解释哪些能力及版本”，Runtime 注册表说明“哪个授权环境现在可执行”。两者不能合并为自注册即可新增可信业务契约。

Descriptor 候选内容：能力 ID/版本、角色标签、输入与输出 schema 引用、人工输入支持、外部副作用类别、资源要求、执行约束和并发上限。InputKeys/OutputKeys 只适合导航，不能替代字段类型、必需性和枚举。

能力 ID 逐字匹配，不自动将 code_review、code-review 和 code.review 视为同一个；首期目录使用一个命名规范，具体清单待冻结。版本建议精确匹配，未知或不支持版本失败，不默默取 latest。

Provider 能力和执行环境限制是匹配条件，不是业务 verdict。Runner 自报支持某能力不能替代 Workspace 授权、凭证状态与隔离检查。mock/scripted 标记进入运行证据，不能满足真实验证门禁。

MVP 的 Provider 由本机 Mac 上的 Runner 调用宿主已安装、已登录的 Claude Code、Codex 等 CLI。静态 CapabilityCatalog 只说明可接受的能力/Provider 协议和最低要求；Runtime 在线报告须把“CLI 存在”“版本匹配”“认证可用”“实际可执行”分开。WorkflowDefinition 不保存 Mac 绝对可执行路径或用户主目录登录文件。节点冻结获准的 Provider 选择规则，Task 派发记录实际 Provider/CLI 版本与运行环境；指定 Provider 不可用时显式等待或返回配置错误，不悄悄切换到另一位成员的账号或另一个模型。项目构建/测试脚本的隔离与模型 CLI 的运行位置分别设计。

历史 source=local/remote 混合了 owner、部署和调度策略。Kowa 不继承其隐式授权：节点需要的能力、运行位置、可访问资源和授权分别判断；单 Runner 也不例外。

## 7. 统一运行器与出站通信

沿用 Host/Capability/TaskSession 的分工思想：运行器负责登记、领取/接收任务、取消、报告与产物通道；Worker 专注能力执行；Provider Adapter 做供应方协议转换。Worker 不自建控制面 HTTP 或私自推进 WorkItem。

本机共享 Provider 登录态是首轮部署约束，不是业务输入或跨机器交接格式。以后增加另一台 Runner 时，该机器独立报告可用 Provider；控制面按冻结能力要求匹配，输入仍来自中心状态、GitHub 和 Artifact Store，不复制第一台 Mac 的 CLI 会话或主目录。

MVP 出站 HTTP 长轮询获取任务、HTTP 心跳/报告已由用户批准，详见 [执行边界](../wiki/architecture/workflow-execution.md)。具体路由、超时、退避和取消下发方式仍需 wire 设计；不能直接恢复历史“控制面 POST 到 Agent base_url”。

无论传输选择如何，都要满足：服务端持久分配 → 执行侧确认与按 Task/派发世代去重 → 上报结果 → 控制面条件接受。响应丢失不等于任务未执行，租约失效不等于外部副作用被撤销。Runner 失联后先隔离旧写回并对账，不能依赖连接内存作为执行账本。

传输幂等、业务 Retry、人工续接、节点 Rerun 分开处理。Task 身份遵守已批准的 [执行尝试合同](../wiki/contracts/execution-attempts.md)，具体字段见 [契约草案](mvp-contracts-draft.md)。批准的依据是用户选择与 Kowa 不变量，不是声称缺失的历史源码已经验证。

### 代码版本在验证前交接

Coder 的可写工作目录只是一轮执行的本地投影。它可在获准项目仓与工作分支中执行本地 Git、主动 fetch/pull/commit/push，使用 Runner 主机个人 `gh`/Git 身份；commit author/committer 也是该机器账号，Web 发起人与 Agent 来源另记。Coder 返回远端可获取的 commit OID 及操作证据；随后 `verify_change` 作为控制面核对节点验证项目仓、工作分支、基线与远端 OID。QA、安全评审与代码评审按该 OID 在各自隔离目录重新获取代码。pull/rebase 或新的 push 改变被测 OID 时，相关下游证据须重新判断适用性。

`publish_pr` 是独立 Runner Capability，只有必需验证和独立评审满足后才由控制面派发；它以同一本机 `gh` 身份创建 PR 并返回 PR 真实身份，控制面再对账。`observe_review` 和 `observe_merge` 仍属控制面外部事实观察责任，等待期间建立只提示的外部操作型 HumanTask。直接给 Coder 本机 `gh` 能力也让它技术上可以提前建 PR：独立发布节点是 Kowa 的正常流程门禁，不是 GitHub 层硬禁止；MVP 不对该例外提供专项检测或清理，不能把节点顺序说成硬隔离。具体账号权限和风险见[权限审计](github-permission-audit.md)。

## 8. 新增 Workflow 的 Kowa 设计流程

1. 在能力目录和已发布模板中定位可复用能力，限定查阅范围，不套用历史“全仓搜索”指令。
2. 编写定义、明确输入输出、人工门禁、资源和失败路径；没有新能力时不改 Worker。
3. 通过 Parse/Compile/发布校验，检查合法选择入口与授权。
4. 审阅规范化定义/golden 差异，并运行行为与负向断言；不得仅重生成 golden 消除红灯。
5. 用隔离执行验证关键路径；必要真实验收按 AGENTS 的人机边界执行。
6. 发布新版本；旧运行继续使用自己的冻结定义。

本项目尚无工程，不写不存在的 UPDATE_GOLDEN/make check 命令，更不自动提交。未来阶段建立真实命令后才形成可执行操作指南。

## 9. 新增 Capability 的 Kowa 设计流程

1. 定义职责、稳定 ID/版本、输入输出与副作用；明确是否真的需要新能力。
2. 建立 schema 与行为样例；若使用模型，再加入版本化 Prompt，确定性能力不强制 Prompt。
3. 实现 Worker 的描述与执行端口，复用运行器提供的 session/产物/进度能力。
4. 在发布目录登记并由 Runner 宣告实际实现；校验 schema、版本、资源、权限和真实/模拟属性。
5. 若要用于流程，再在 Workflow 中引用和绑定；能力可以被多个定义复用。
6. 验证取消、输入错误、结构化输出、人工等待/续接、产物故障与重复报告，最后验证实际业务目标。

新增 Provider 主要改 Adapter 与能力兼容性声明；新 NodeType 才涉及编译器/执行器语义。不能把改 Prompt 当作整个新能力已经完成。

## 10. 本轮结论边界

可沿用：声明式定义、分层校验、冻结运行、显式数据流、统一运行器、能力目录、非阻塞交互、独立协议测试。

已经批准：首期单条固定流程、后续复用能力扩展、出站长轮询和 Task 尝试身份。待审技术细化：YAML 作者格式及发布实现、精确版本匹配、节点/条件最小集合、静态目录 schema、路由/字段与参数。不得把基线批准扩展解释为所有字段均已冻结。

对应目标断言见 [验收矩阵 B01—B12](../Kowa验收与运行/MVP验收矩阵.md)。
