# 执行尝试与重复投递合同

状态：active（行为基线已批准，未实现）。文档行为版本：1。最近核验：2026-10-01。

Owner：Execution 领域。Producer：控制面执行管理与统一运行器。Consumer：Worker、Workflow 结果应用、HumanTask 续接、审计与 Web。wire 与 schema 由 backend:S02 的 `kowa.workflow-execution.v1` 拥有（见 [Workflow/Execution v1 契约](workflow-execution-v1.md) 与 [`api/workflow-execution/v1`](../../../api/workflow-execution/v1/README.md)）；本文仍只拥有行为语义，不定义 HTTP/wire 字段或数据库表。

## 1. 身份语义

| 事件 | Task 身份 | 有效输入 |
| :--- | :--- | :--- |
| 同一次执行重复投递/报告 | 复用原 Task | 不变；不能重复 Execute 或重复推进 |
| 执行错误后获准 Retry | 新 Task，关联前一次尝试 | 相同业务有效输入；传输凭证可更新但不改变业务内容 |
| 人工答复后续接 | 新 Task，关联前一次尝试及已接受答复 | 保持原冻结上下文，增加明确的人答复 |
| 业务返修/Rerun | 对新节点轮次建立相应 Task | 引用新反馈/上游版本；不能伪装成相同输入 Retry |

Provider session_ref 可以用于优化上下文恢复，但新 Task 不必拥有新 session。反过来，有 session 也不证明用户已批准或某次尝试已经完成。

## 2. 执行与结果

运行器区分交付去重与执行重试。同一 Task 状态未知时先查明，不以进程重启为由盲目重新 Execute；确需再次执行，由控制面授权新尝试。每个尝试保留输入、开始/结束、结果、错误和关联。

人工输入请求表示本次执行已让出运行资源，NodeRun 等待控制面接受答复；不得让 Worker 进程承担长期人工等待真源。答案接受与后续执行意图一致持久化后，再发起续接尝试。

结果接受验证当前任务、租约/派发身份、对象范围和输入版本。相同请求的相同结果幂等；相同身份不同结果冲突。旧结果仅保留历史/外部事实，不得覆盖当前有效轮次。

## 3. 失败与外部副作用

幂等报告不是外部操作 exactly-once。GitHub 操作结果未知时先对账，不能单凭创建新 Task 自动重做写操作。更换执行身份、已失效授权或资源冲突都可能要求先暂停处置。

结果必须区分执行结束与业务 verdict。progress 不放行，completed 不代表评审通过，awaiting_input 不代表工作项成功。

## 4. 行为走查样例

以下身份仅作示意，不是真实运行证据，也不规定 ID 编码格式。

| 顺序 | 事件 | 必须保留的关系 |
| :--- | :--- | :--- |
| 1 | T1 消费 I1 后请求人工补充 | 保存 T1 的输入/结果、候选内容和 HumanTask H1，执行资源让出 |
| 2 | 用户对 H1 提交有效答复 R1 | 持久化答复；新输入 I2 明确关联 I1、候选版本和 R1 |
| 3 | 派发续接 T2 | T2 关联 T1 与 I2；可复用原 Provider session，但不修改 T1 |
| 4 | T2 的接收响应丢失，重复投递 | 仍是 T2/I2，先查执行状态，不新开第二次 Execute |
| 5 | T2 执行失败并获准 Retry | 新 T3 关联 T2，仍消费 I2；失败历史保留 |
| 6 | T2 迟到成功报告 | 按旧尝试审计/对账，不能覆盖当前 T3 或重复推进 |
| 7 | T3 的有效结果被接受 | 由控制面根据业务结果决定节点下一步，不由 session 或进度决定 |

第 5 步若涉及结果未知的外部写操作，必须先完成第 3 节要求的对账，不能仅因超时就建立可执行的 T3。

## 5. 版本与验证边界

改变尝试身份、Retry 输入保持或答复关联语义属于行为合同变化，需要明确版本与迁移设计；当前没有历史消费者，无需恢复旧项目的 Task ID 兼容路径。

目标测试应覆盖重复投递、报告响应丢失、Retry 输入一致、人答复续接、旧报告迟到以及外部副作用未知。具体验收入口见 [MVP 验收矩阵](../../Kowa验收与运行/MVP验收矩阵.md)。API 序列化、租约时间和重试预算参数仍未冻结。
