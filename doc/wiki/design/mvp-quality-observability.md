# MVP 质量、评测与可观测设计

状态：active（首期质量职责与证据合同；未实现）。最近核验：2026-09-27。

本文拥有跨端质量/评测的详细业务边界。总体约束见 [common](../../common.md)，交付顺序见 [MVP 流程](mvp-delivery.md)。具体检查命令、测试仓库、数据集和量化阈值需在实施合同及真实环境中确定，本文不记录虚构的运行结果。

## 1. 同步交付门禁

MVP 对当前有效代码提交要求：仓库声明的构建与必需测试通过、QA 验证满足验收标准、独立代码评审和安全评审没有未处置阻断意见、当前 PR head 上有另一名有权用户提交的适用 GitHub Review。PR 创建者与提交 author/committer 是 Runner 机器的个人 GitHub 账号，WorkflowRun 发起人与 Agent 来源分别留存证据。合并后还须针对实际合并结果通过集成验证，才能关闭 WorkItem。

模型评审完成执行不等于评审通过；结构化 verdict 为 `needs_revision` 时按有界返修处理。模型输出无法解析、摘要缺少证据或安全检查无法完成时，不能把空结果算作 pass。人工处置可改变需求/策略并触发新版验证，不能把已经失败的确定性测试改写成通过。

首期不设没有数据支撑的通用模型评分阈值。模型质量、过程质量与工作流质量可以被观察和校准；只有交付合同明确指定的质量/安全条件是同步门禁。

## 2. 异步评测

离线回归、成本/延迟/干预率统计和持续校准异步运行。知识更新建议与异步评测失败分别记录与重试，不反向改写已经确认的交付成功。把一个模型评分提高不能抵消缺少人工批准、GitHub 合并事实或集成验证。

Kowa 持有评测定义、输入、结果、证据关系与是否阻断的业务决定。自托管 Langfuse 提供可替换的轨迹和评测后端；Langfuse 中的 trace 或 score 不是 WorkflowRun 状态真源。Prompt 的源码、审批和发布仍由 GitHub PR 负责。

若明确配置为同步门禁的评测后端不可用，控制面保持未满足并记录恢复条件；非门禁轨迹发送失败作为独立观测/补传问题，不假装节点成功与否发生变化。两种情况由同一冻结交付合同决定，不能在故障时临时降级。

## 3. 最小证据关联

跨端事件和轨迹至少能关联 Workspace、WorkItem、WorkflowRun、NodeRun/轮次、Task/尝试、Capability、Runner、Provider/模型、Prompt 与定义版本、知识/代码/输入摘要及 ArtifactRef。事件区分 `progress`、执行结果、业务 verdict、人工答复、外部 GitHub 事实与关闭证据。

展示层显示事件时间与最后成功观察时间。Runner 心跳只能证明环境仍可联系，不能证明能力仍在产生业务进度；GitHub 主动查询失败也不能让旧 Review/合并结果冒充最新事实。

日志和 trace 以引用或脱敏摘要展示。OAuth client secret、成员用户令牌、Runner 凭证、Provider 密钥、仓库中的敏感内容和完整用户输入不能因便于排障被无条件送入 Langfuse。采集前治理比事后 UI 隐藏优先。

## 4. 单 Runner 非功能基线

- 同一业务仓库同一时刻只能有受控的一条写入线；无依赖的只读任务可并行，但不得越过资源与沙箱策略。
- 运行恢复以 PostgreSQL 状态、GitHub 提交和 ArtifactRef 为准；本地目录删去后，读消费者仍可重建输入。
- 已发布给下游或被关闭清单引用的证据须可获取；孤立上传另行清理。开发验收期间不主动清理核心证据。
- 收集任务排队、模型执行、人工等待、GitHub 对账与集成验证耗时，分别记录成功率、恢复次数和资源使用。没有真实负载前，不写虚假的 SLA 或容量数字。
- 真实团队验收前，按 [验收方案](../../Kowa验收与运行/MVP真实集成验收方案.md)确认本机磁盘、容器/进程隔离、备份与失效恢复能力；本地 Mac 可运行不是生产部署已就绪的证据。

## 5. 失败归类

业务验证失败、模型判断波动、能力协议错误、执行环境故障、外部 GitHub 状态未知与权限拒绝分别记录。`OBSERVATION_ONLY` 只适用于确定性合同与证据仍合法的波动；若必需门禁缺证据或 Kowa 状态转换错误，则按阻断失败处理。
