# Kowa 决策记录

## 控制面与执行面分离

Kowa 采用控制面与执行面分离的架构。首期使用模块化单体控制面和独立 Runner，不提前拆分微服务。这样既能控制早期研发和运维复杂度，也能支持 Runner 跨机器部署和后续独立扩展。

## 使用中心真源完成跨机器交接

PostgreSQL 保存工作流和任务状态，GitHub 保存代码、提交和 PR，Artifact Store 保存非代码制品与证据。本地仓库、worktree 和运行目录仅是可重建投影。采用这一方式是为了避免节点之间依赖同一台机器或隐式本地目录，并支持失败恢复和审计。

## 多仓库需求按仓库拆分工作项

跨代码仓库、Web 仓库和 IDL 仓库的需求按仓库拆分为相互依赖的子工作项。涉及跨仓接口时，IDL 或协议仓库作为接口定义真源，不因接口简单而省略。这样可以明确仓库责任、契约依赖和并行执行边界。

## 首期采用 Web 交互入口

Kowa 首期只实现 Web 交互入口，飞书等渠道后续通过 Adapter 接入。这样可以控制首期范围，同时避免未来渠道能力侵入核心领域。

## Kowa 持有评测领域和数据闭环

Kowa 自建评测领域模型，首期接入自托管 Langfuse，并使用 OpenTelemetry 传递执行轨迹。Langfuse 不作为工作流状态真源，Prompt 的源码、审批和发布仍以 GitHub PR 为真源。这可以保留核心数据与流程控制权，并降低对单一评测产品的依赖。

备选方案包括 LangSmith、Phoenix 和 OpenAI Evals。LangSmith 与 LangChain/LangGraph 生态结合较紧且自托管约束更强；Phoenix 更偏开放标准下的可观测与评测，首期 Prompt 管理和一体化闭环不如 Langfuse 集中；OpenAI Evals 适合作为供应商侧评测工具，但不足以承担跨模型、跨工作流的统一评测后端。后续仍可通过统一接口增加其他实现。

## 外部集成采用端口—适配器模式

Kowa 核心为外部能力定义稳定端口，由适配器完成供应商协议、SDK 和领域对象之间的转换，不在核心工作流中直接依赖外部产品。评测端口命名为 `EvaluationBackend`，Langfuse 实现命名为 `LangfuseEvaluationAdapter`；统一使用 `Adapter`，不使用 `Adaptor`。同一模式用于 Coding Agent、Artifact Store、Capability Worker 和协作渠道接入，其中 Claude Code、Codex 等 Coding Agent 共享统一任务与结果协议，以支持供应商替换、多模型路由及交叉评审。相比直接调用供应商 SDK，该选择增加了一层转换，但保留了可测试性、替换能力和核心领域边界。

## Replay 使用冻结快照和隔离运行

Replay 不动态依赖源 WorkflowRun 的可变记录，也不默认从某节点重跑全部下游。系统先冻结源运行的工作流定义、节点输入输出和产物引用，再创建新的隔离 WorkflowRun；未选节点物化冻结结果，只有明确选中的节点真实执行。相比直接查询源运行或完整重跑，该方案增加了快照存储和副作用治理成本，但能控制变量、降低回归成本，并保证实验可复现且不修改源运行。

## 核心编排按职责选择基础设施

核心编排不预先绑定 Redis、Kafka、Temporal，按已确认需求选择。这不同于取消独立 Runner、持久任务或跨机器产物交接。相比预先部署一套通用分布式组件，这一选择降低早期运维成本，同时要求 Kowa 明确承担自己的持久化、幂等与恢复责任。

评测等外部子系统的必要依赖单独列明。首期自托管 Langfuse 的部署依赖不能被这一决定排除，也不能自动成为 Kowa 工作流状态真源。具体组件及版本在部署设计中核验。

## 固定成熟版本的技术栈

项目初始版本固定为 Go 1.25.14、Node.js 22.23.2、pnpm 10.34.5、React 18.3.1、TypeScript 5.9.3 和 PostgreSQL 17.11。该决定优先考虑已有生产实践、工具兼容性及项目当前需求，而不是直接采用最新主要版本。

## 使用 mise 管理项目级工具链

本地开发使用 mise 根据仓库中的 `mise.toml` 切换项目工具版本，不修改本机全局 Node.js 和 Go。CI 与容器独立固定相同版本。这样既能保证项目环境可复现，也能避免影响依赖全局环境的 Codex、Claude Code 等工具。

## 优先复现历史核心能力并沿用后端技术路线

选择以历史设计为主要起点，采用标准 net/http、Uber Fx、分层架构以及 PostgreSQL 的关系字段与 JSONB 分工。相比从头重新选型，这能集中精力处理 GitHub 适配和历史缺口；相比直接复制历史实现，仍须核对残缺代码、冲突文档、内部平台依赖与失效门禁。历史模块和数据模型按同样原则优先参考。

## MVP 先完成单业务仓库交付

选择先验收一个业务仓库的完整交付，配套知识库只读，而不在首个 MVP 中实现多仓父子工作项与 IDL 供给编排。单仓已经能检验知识绑定、人工门禁、独立评审、产物交接及恢复；直接多仓会增加跨运行依赖、版本传播和部分失败汇合成本。仓库身份和版本保持显式，后续扩展无需依赖本地目录假设。

## 单 Runner 部署但保留交接边界

选择首期部署一个独立 Runner，并验证无共享执行目录的交接。备选是同进程和共享目录耦合，或首期就实现多机并发与高可用。前者会使后续分布式改造涉及大量节点，后者提前增加调度和运维成本；所选方案保留持久任务、租约和产物协议，推迟容量与高可用优化。

## MVP 使用内置流程并后置 Replay 操作

选择首期只交付一条固定内置流程及真实 DAG 展示，不做多模板选择，也不开放任意定义文件编辑或 Web 拖拽编排。定义与能力保持分离，使后续新流程复用已有能力、已有流程通过新版本增加 Agent 节点；相比把首条流程写死在业务分支中，这保留扩展边界，且不提前交付通用编排产品。首条验收场景使用已有仓库的小型功能或缺陷修复，D2C 和部署预览不作为必需能力。

恢复先覆盖 Retry、返修和必要 Rerun，Replay 操作后置。相比同时交付隔离回放，这减少首期副作用治理与产品入口的范围；代价是首期不能操作 Replay，但仍须保存不可变输入与证据，且不改变既定 Replay 语义。

## 知识建议与业务关闭分离

选择系统推荐知识、用户确认绑定，运行期只读；交付后生成知识建议 Artifact，而不自动提交知识库 PR。建议失败不阻断业务关闭，单独保留待处理结果。相比直接写回知识库或等待知识流程才能关闭，这降低第二条仓库写入链路对 MVP 的影响，同时保留人工审阅与后续重试出口。

## 有界自动返修与人工处置

选择为方案、代码自动评审分别设置返修预算，耗尽后交人处理；不采用无限自动回环或耗尽后自动通过。预算规则见 [MVP 流程](wiki/design/mvp-delivery.md)。这控制成本与无效循环，代价是需要明确的人工恢复入口；人工决定不能把确定性失败改写为测试通过。

## 交付终点与合并后修复

选择人工批准合并并完成集成验证作为关闭终点，而不是仅生成可评审 PR，也不要求首期部署。已关闭工作项后续变化创建关联新项，不重开原交付；尚未关闭且合并后验证失败时，经人工确认在原工作项下开启修复运行与新 PR，不自动回滚。相较持续改写原交付或自动撤销合并，这保留版本和责任边界，但必须能展示运行与修复关系。

## 真实执行尝试使用独立 Task 身份

选择每次真实重新执行创建新 Task，重复投递则复用原 Task。备选是沿用历史同一 Task ID 加执行轮次和可变输入。所选方案使每次有效输入、人工答复、执行结果与失败独立可追溯，与 Task 作为执行尝试的定义一致；代价是记录更多尝试关联，Provider session 不能再被当作任务身份。Retry 保持输入，人工续接明确关联前一次 Task 和已接受答复。

## MVP Runner 使用出站 HTTP 长轮询

选择出站长轮询获取任务，以 HTTP 完成心跳和报告；备选为首期出站持久流。单 Runner 场景下，长轮询的实现、重连和排障路径较简单；代价是需要设计请求等待、退避和取消延迟。可靠性仍由持久任务、租约、去重和外部对账提供，不由连接承担。运行器端口与传输解耦，后续改用持久流不改变业务合同，也不恢复控制面主动访问 Runner 入站端口。

## MVP 使用 GitHub App 用户授权登录并由 Kowa 管理会话

选择 GitHub App 的 OAuth Web 流程识别用户，由 Kowa 服务端管理会话和 Workspace 授权。备选为首期单用户无登录、本地密码账户或把 GitHub App installation 当作用户身份。选择此方案是因为 MVP 面向小团队多人协作，必须区分个人、仓库安装和执行环境的授权；代价是需要回调、会话、CSRF、成员初始化与撤销能力。首条真实验收仅在本机 Mac 的同机浏览器执行，具体回环 HTTPS 地址和证书由环境准备确定。

## MVP 直接使用 Runner 本机个人 gh 身份执行 GitHub 操作

选择每台 Runner 预配置可用的 Coding Agent Provider 与个人 `gh`/Git 登录，由获准的执行任务在本机完成项目仓库的 clone/fetch/pull、本地 commit 和工作分支 push；必需测试与独立评审通过后，由独立 `publish_pr` 执行节点使用同一本机 `gh` 创建 PR。Web 使用 GitHub App 登录，但 Web 发起人不自动成为 GitHub 写入身份。commit author/committer、push 和 PR 创建者归 Runner 主机的个人账号，Kowa 单独记录 WorkItem/Run 发起人及 Agent 来源。备选为 Server 用每位 Web 用户的 GitHub App 用户令牌执行发布、每任务委派成员令牌给 Agent、专用机器账号或受控 Git 通道。所选方案能较快验证历史型 Agent 自主 Git 工作流并复用本机工具状态，代价是 GitHub 写入不能按 A/B Web 用户区分，个人账号访问范围和凭证生命周期不受 Kowa 精细控制，同一 macOS 账号下的 Agent 可能访问宿主更多仓库和凭证；独立发布节点也不能凭自身顺序在 GitHub 层阻止 Coder 提前建 PR，MVP 不为此例外提供专项检测/清理。只能在已知可信仓库和明确 GitHub 分支保护、审计与负向验收条件下评价首期能力，不能宣称企业级硬隔离已经实现。

## 可恢复执行失败暂停当前运行，终结失败才结束运行

选择可恢复的节点执行失败使当前 WorkflowRun 暂停，由明确 Retry/Rerun 命令继续；`FAILED` 只表示本次运行已经终结。备选是每次节点失败都终结运行并新建 WorkflowRun。所选方案保留一条交付运行的推进权与失败历史，允许相同输入的 Retry 和受控 Rerun；代价是需要明确暂停原因、预算、授权及旧结果隔离。合并后集成验证失败如需改代码，仍在未关闭 WorkItem 下建立关联修复运行与新 PR，旧运行终结后让出推进权。

## GitHub 人工操作使用外部事实收束的 HumanTask

选择在等待 GitHub Review 或人工合并时建立外部操作型 HumanTask，向用户提示目标 PR 和适用提交；由 Kowa 核对 GitHub 事实后自动收束，不接受第二次 Kowa 批准点击。备选是在运行投影中仅显示系统观察状态、不建立人工待办。所选方案使真实外部人工操作进入统一待办和审计入口；代价是必须区分待办解决与业务门禁通过，并在 PR head 变化时使旧待办失效，不能让提醒状态替代 GitHub Review 或合并事实。
